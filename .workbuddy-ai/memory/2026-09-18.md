- 不动 Rust：现有 `query_openox` 已正确处理 `start_date=end_date` 场景

### 一次查询 HTTP 请求量统计
| Provider | 请求数 | 内容 |
|---|---|---|
| openox | `1 + ceil(总条数/100)`，默认 1 次 | `GET /api/v1/subscriptions/current` + 分页 `GET /api/v1/usage?page=N&size=100&start_date&end_date`（最多 500 页硬上限） |
| owlai | 1 | `GET https://api.owlai.tech/v1/usage?days=1&timezone=Asia/Shanghai` |
| openai-compatible（newapi 通用） | 1 | `GET <relay>/v1/usage?start_date&end_date&days=90&timezone=...` |

并发冲击：openox 是顺序分页（单连接复用 reqwest::blocking::Client），非并发；当天条目通常 < 100 → 一般 1+1=2 次 HTTP。最大风险日（条数 > 100）也只多 1 次，对站点的冲击可忽略。**结论：不会对供应商造成并发冲击，无需并行化优化。**

## 用量插件 v13：桥未就绪不发请求 + 自适应重试

用户反馈"正在连接用量插件…"状态停留很久，并同时撞"用量请求超时"。根因是 fetchUsage 入口先调 `/v1/usage/settings` 与 `/v1/usage/query`，撞桥自身 20s/70s 硬超时。

### 改动清单（v13）
- `plugins/xuan-usage/scripts/usage-header.user.js`
  - REVISION 升级到 `builtin-2026-09-18-v13`
  - `state.bridgeReady: false` 初值
  - 新增 `probeBridge(timeoutMs=1500)`：调 `/v1/usage/settings` + 1.5s 短超时，作为桥握手探针；settings 是本地 JSON 读，瞬时返回，不会撞超时
  - `fetchUsage()` 入口先 probe：未通返回 `{ status: "loading", provider: "unknown", bridgeReady: false, message: "正在连接用量插件…" }`，**不再发起任何业务 RPC**
  - 业务路径第 1 行 `state.bridgeReady = true`，下次 setState 合并时带上
  - `refresh()` 算出 `nextRetryMs` 自适应重试间隔：
    - `bridgeReady === false` → 3000ms（轮询等待插件上线）
    - `status === "failed" | "disabled"` → 30_000ms（避免对供应商/桥施压）
    - `status === "ok"` → `config.refreshMinutes * 60_000`（按用户配置）
  - `schedule(delayMs)` 接受可选延迟参数，internal 也清掉旧 timer
  - `renderPanel()` body 区分 `!bridgeReady`（"正在连接用量插件…"）与 `loading`（"正在读取用量…"），错误提示不再误标为"用量请求超时"
  - `settingsHtml()` 把 `state.provider === "unknown"` 改为 `!state.bridgeReady`，更准确表达"桥未就绪"
- `plugins/xuan-usage/scripts/usage-header.user.test.mjs`：REVISION 改 v13；新增「探针 & 自适应重试」一组断言覆盖 `probeBridge(1500)`、`bridgeReady: false`、`function schedule(delayMs)`、`nextRetryMs = 3000` 与 `30_000` 等关键路径

### 行为变化前后对比
| 阶段 | v12 | v13 |
|---|---|---|
| 启动后第一次自动刷新 | 同时发 settings(撞 20s 超时) + query(撞 70s 超时)，最快 70s 才能报错 | 仅发一次 settings 探针，1.5s 后停下来；UI 稳定显示"正在连接用量插件…"，3s 后再次握手 |
| 桥一直没起 | 用量请求超时 → schedule 等 5 分钟 | 一直停留在"正在连接用量插件…"，3s 轮询握手 |
| 桥起来 | 等下一轮刷新（5 分钟） | 3s 内自动恢复读取 |
| 某次用量查询失败 | 等 5 分钟 | 30s 后短重试 |

### 测试
- JS：`node --test usage-header.user.test.mjs` → 5/5 通过
- Rust：`cargo test --test provider_contract` → 6/6 通过（未触动后端）

## install-xuan-features.bat：安装时一并结束并自动重启 Codex++ 主程序

用户反馈安装脚本只清理 Xuan 插件进程、保留 Codex++ 主程序，每次都要手动退出再重开。

### Codex++ 主程序事实（重要）
- 安装目录：`D:\Codex++`（注册表 Uninstall 项 DisplayName=Codex++ 的 InstallLocation）
- `codex-plus-plus.exe` = 无窗口静默启动器（日常主程序，承载 Codex++ 会话）
- `codex-plus-plus-manager.exe` = Tauri 管理控制台（identifier `com.bigpizzav3.codexplusplus.manager`）
- 用户数据：`%APPDATA%\Codex++\user_scripts`

### 改动清单
- 新增 `scripts/restart-codex-plus.ps1`（UTF-8 BOM + CRLF，与既有 ps1 一致）
  - `-Action Stop`：按进程名 + ExecutablePath 核实后强制结束两个主程序进程，把路径写入 `-StateFile`（主程序在前）；结束前复核 CreationDate/ExecutablePath 防误杀
  - `-Action Start`：优先按 StateFile 原样拉起；为空时从注册表 InstallLocation / `%LOCALAPPDATA%\Programs\Codex++` 等发现主程序；已运行的同名进程跳过
- `install-xuan-features.bat`
  - 步骤 5 开头先 Stop（在清理 Xuan 插件进程之前）
  - 步骤 5 之后所有失败分支由 `exit /b 1` 改为 `goto :fail`
  - 新增 `:restart_codex_plus`（步骤 7 调用）与 `:fail`（先恢复启动再 exit 1）
  - 结尾文案改为「安装已结束旧任务的插件进程与 Codex++ 主程序，并自动重新启动 Codex++」
- `scripts/stop-xuan-plugin-processes.ps1`：文案改为「Codex++ 主程序由安装脚本统一结束并重启」

### 踩坑
- PS 5.1 下 `Split-Path -LiteralPath <path> -Leaf` 不是合法参数集（「无法使用指定的命名参数解析参数集」），改用 `[System.IO.Path]::GetFileName/GetDirectoryName`
- 用 Python 改 .bat 必须保持 CRLF（`newline=''` 会把 CRLF 写成 LF，label/goto 会失效）
- ps1 含中文必须 UTF-8 BOM
- WorkBuddy 的 PowerShell 工具环境：`$env:OS` 为空、执行策略 Restricted（测试需 `Set-ExecutionPolicy -Scope Process Bypass` 并手动设 `$env:OS`）；会话结束会回收 Start-Process 拉起的子进程（真实 cmd 环境不会）

### 验证
- 真实 Stop：结束 2 个进程，StateFile 记录两条路径，残留 0
- 真实 Start：按 StateFile 拉起两个 exe，均成功
- `-WhatIf` 会连带跳过 `Set-Content`，调试时勿据此判断状态文件逻辑
