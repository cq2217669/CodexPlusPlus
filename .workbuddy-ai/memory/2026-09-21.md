# 2026-09-21

## 调研：ZCode 开源是否替代 Codex++（结论：不替代）

背景：智谱 Z.ai 的 ZCode 因"偷传代码"安全事件（社区质疑本地文件路径外传至阿里云 OSS 桶）完成整改后，于 2026-09-21 开源（github.com/zai-org/ZCode）。用户问是否可以把本项目功能全迁到 ZCode、是否更稳定。

**核实到的事实**
- ZCode = Z.ai 自研 AI 编程工作台（coding agent harness），三形态：Electron Desktop / Web / 终端 TUI；TS + pnpm monorepo；License **Apache-2.0**（Copyright 2026 Z.AI Co., Ltd）。
- `THIRD-PARTY-NOTICES.md` 中**完全没有** codex / codex-rs / OpenAI Codex CLI 相关声明 → 不是 Codex CLI 的 fork，是独立 harness。
- 仓库仅 1 个 commit（`feat: open source`，作者 MBearo），Issues **0 open / 0 closed**，尚无社区治理与外部贡献历史。
- 自研 provider 体系：`ZCODE_BUILTIN_PROVIDER_CONFIG_FILE`、`packages/provider`、`packages/provider-node`，不吃 codex 的 `config.toml` / `model_catalog_json`。

**判断（三条硬理由）**
1. **层级不同，不是替代关系**：Codex++ 是挂在 OpenAI Codex **官方桌面应用**外面的外挂层（CDP 注入 + 生成 `config.toml` / `auth.json` / `model_catalog_json`，Rust/Tauri）；ZCode 是自带界面与运行时的另一个客户端。用户前提是"我用官方 Codex 客户端"，ZCode 开源不改变这个前提。
2. **功能不可搬**：Codex++ 一半以上功能（插件市场解锁、界面注入、中文界面、粘贴修复、会话宽度、Goals、Stepwise）存在的唯一理由是"官方 app.asar 不可改"。ZCode 自有源码，这些需求在那边**根本不存在**，搬过去是零价值。剩下的上下文窗口/供应商功能依赖 codex 的 `model_catalog_json` 契约，迁过去只能按 ZCode 契约**从零重写**，不是复用。
3. **License 方向不兼容**：Codex++ 是 **AGPL-3.0-only**，ZCode 是 **Apache-2.0**。AGPL 的传染性要求衍生作品整体 AGPL，**AGPL 代码不能并入 Apache-2.0 项目**。代码级合并法律上直接不成立，只能"读思路 + 独立重写"。
4. **"更稳定"无依据**：0 issue / 0 PR / 单 commit，未经过社区检验；且刚因数据外传事故被迫开源。把 API Key / 凭据管理交给它，风险方向是反的。

**对本 fork 主线的影响：接近零。** issue #1171/#931 的 per-model context 依赖 codex 原生 `model_catalog_json`，ZCode 不吃这套。

**唯一值得做的跟进**：把 ZCode 当"平行参考实现"读一遍（provider 抽象、SSH/WSL 远程、CLI 打包分发、`patches/` 机制），有可借鉴处再单独记录；若未来 ZCode 成为主流，可评估**新写**一个 ZCode 版的 provider/context 配置工具（新项目，非迁移）。

## 调研：ZCode 接中转站后工具调用能否赶上 ChatGPT 官方客户端

来源：ZCode 官方文档 `zcode.z.ai/cn/docs/` 的 `configuration`（连接模型）、`browser-use`（浏览器自动化）、`agents`、`ADE-tools` 四页。

**ZCode 供应商接入能力（事实）**
- 支持自定义供应商，兼容 **Anthropic / OpenAI(Chat) 协议**，可填自定义 Base URL + API Key → **中转站可以接**。官方文档直接给了 OpenRouter 的接入步骤（`https://openrouter.ai/api`）。
- 协议只有两套：`OpenAI 接口地址` + `Anthropic 接口地址`。**文档全文未出现 Responses API** → ZCode 走 Chat Completions / Anthropic Messages，与 OpenAI 官方 Codex 客户端的 Responses API 不是同一套。
- 内置浏览器：**Browser Use 官方插件**，默认开启，**仅桌面端**。Agent 可打开网址、点击、填表、滚动、截图。安全边界：网页文字不当指令、**暂不能上传文件**。有视口自由尺寸模式。
- 预览面板：PDF 翻页缩放、HTML 用内置浏览器打开、Mermaid 大图、图片图集、表格大预览窗口；终端面板集成在预览面板中。
- **ZCode 官方文档里没有"画中画"这个功能**。最接近的是浏览器面板自由尺寸 + 预览面板浮窗，以及社区悬浮窗插件（如 `ssbh163/ZCode-Usage`）。这些全是**本地 UI**，与中转站无关。

**中转站降级的直接证据（官方文档自述）**
1. 推理档位不兼容：*"同名模型的第三方部署，接受的档位可能与官方端点不一致。例如 DeepSeek V4 系列在 ZCode 中的最高档按官方端点约定发送 `max`，而部分第三方部署只接受 `xhigh` 及以下——此时选最高档会返回 400 参数错误"*。
2. **自定义请求参数静默丢弃**：`~/.zcode/v2/config.json` 供应商 `options` 只识别 `apiKey`、`baseURL`、`apiKeyRequired`、`headers`；手写 `reasoning_effort`、`vl_high_resolution_images` **不进请求体、也不报错**（静默失败，最难排查）。
3. 图片能力三态判定：支持 / 不支持（请求前移除并转文字提示）/ **能力未知**（不拦截，服务端不支持则直接报错）。浏览器截图理解依赖多模态——官方指定 **GLM-5.3-Flash** 为截图理解/看图分析模型。且同一模型经不同协议判定不同（GLM-5.2 走 Anthropic 兼容可带图，走 OpenAI Chat 兼容则按不支持处理）。
4. 上下文窗口规则：自定义供应商模型可改；Coding Plan 内置模型由**服务端下发**，本地改会在下次同步被覆盖；`[1m]` 后缀固定 1M。**自动压缩无开关、无阈值可配**，预留约 3.4 万 token（128K 窗口约 9.4 万触发，1M 窗口约 96.6 万触发）。→ 对比 Codex++ 的 per-model auto_compact，这是 ZCode 的明确短板。

**结论**
- 工具"能不能跑"= 本地，中转站不参与 → 不受影响，ZCode 这块甚至强于官方客户端（能驱动本地浏览器 + 直接改项目文件）。
- 工具"用得对不对"= 模型决策 + 传输保真 → **中转站重灾区**，这是"赶不上官方客户端"的真正原因。
- 公平对比提醒：ChatGPT 官方客户端**接中转站同样会降级**（这正是 Codex++ 存在的场景）。要对比应是「ZCode+中转站 vs 官方客户端+中转站」或「ZCode+官方直连 vs 官方客户端直连」，不能混。
- 若走 **GLM Coding Plan 官方直连**（非中转站），ZCode 的主场优势才成立（文档反复强调针对 GLM-5.3 深度联调）。
- 建议的验证方法：同一句指令（如"打开 localhost:5173，切深色模式，截图给我"）在三种通道各跑一遍，记录截图能否被理解、多步操作能否连续、是否 400、压缩点位置。

## 需求明确：用户想弃用外挂模式，改为可二开桌面端

用户原话要点：中转站"和 GPT 官方身份特征高度吻合，codex 执行也会认为是官方的 GPT"；桌面端想二开；现在外挂模式"有些影响桌面端的性能，有时会卡一卡的"。

### 外挂模式卡顿的技术原因（对本项目自查有用）
1. **CDP 附加**：DevTools Protocol 一旦挂上，Chromium 需保持调试插桩开启，渲染进程有额外固定开销。
2. **注入脚本 hook DOM + MutationObserver**：官方 React 每次重渲染都触发回调，而它跑在**与官方 UI 同一个渲染主线程**上 → 直接争抢。
3. **额外本地辅助服务跳数**：协议转换（Chat Completions → Responses）多一跳延迟。
4. 可能的周期性状态轮询。
→ fork 掉前三条全部消失。

### 关键发现：Codex 官方开源仓库自带 GUI 接口
`openai/codex` 的 `codex-rs/` 下有完整的 **app-server 家族**：`app-server`、`app-server-client`、`app-server-daemon`、`app-server-protocol`、`app-server-transport`、`app-server-test-client`；顶层还有 `sdk/{python,typescript,python-runtime}`。

从 `codex-rs/app-server/README.md` 确认这是给本地 UI 客户端的 **JSON-RPC 服务**，已见 RPC/字段：
- `model/list`（会校验启动 provider 是否满足当前 managed provider 要求，不满足返回 JSON-RPC `-32600` 要求重启）
- `thread/start`（含 `daybreakEnabled`、`experimentalApi` opt-in）、`thread/metadata/update`、`thread/started` 通知
- `userVerification/cancel`（实验性，可取消原生用户验证）
- **`mcpToolCall.mcpAppUi`** 带 `resourceUri` 与 **`preferredModelDisplayMode`（`inline` | `fullscreen`）** → **用户关心的"画中画"能力，官方协议里已定义**
- 另有 `context-fragments`、`code-mode`、`config-schema`、`collaboration-mode-templates` 等 crate

### 推荐路线
**fork `openai/codex`（Apache-2.0）→ 自写桌面 UI，通过 app-server JSON-RPC 对接。**
理由：① 协议零成本，用户的中转站一行配置都不用改；② 官方给了 GUI 接口 + TS/Python SDK，不必 CDP 注入；③ 画中画在协议里已定义；④ Apache-2.0 允许闭源改造（留 NOTICE）；⑤ Rust 内核 + 自选 UI 技术栈。

备选：**OpenCode（MIT 最宽松，自带 Electron 桌面端，TS 二开门槛最低）**；**Goose（Apache-2.0，有 `CUSTOM_DISTROS.md` 教做自定义分发，`crates/goose-providers` 抽象干净，`crates/goose-context-management` 独立 crate 对本项目 per-model context 有参考价值）**。

### 待验证三点
1. 中转站能否被新 harness 直接用（协议 + 认证形态）——用户的"官方身份特征模拟"可能是为过 Codex 客户端校验，换 harness 后可能不再需要。
2. app-server 的版本稳定性（RPC 里有 `experimentalApi` opt-in，说明有实验性 API，升级会动）。
3. 上游同步成本（fork 开源项目仍要跟 release，但比逆向闭源 Electron 可控得多）。
